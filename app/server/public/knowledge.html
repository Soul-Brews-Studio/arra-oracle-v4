Configuration

The bank you enter here is BOTH the admitted route scope for /api/knowledge/:bank/:method and the workspace_name every request body must carry — the transport rejects a request whose body names a different workspace than the route (see src/knowledge/transport.ts).

What this explorer does NOT do (honestly, not silently)

There is no workspace/peer/session LISTING endpoint anywhere in this transport — only get-by-name and get-by-id lookups (getPeer, getSession, getMessage, getVocabulary, getTerm all require you to already know the exact name or id). Navigation below is therefore typed identifiers, not a browsable tree. Conclusions/Traces/History have no backing kernel wired into this transport (registry.ts explicitly excludes session-link, lifecycle, trace and search-chunk for now) — their tabs are disabled rather than rendering an empty shell. Publish/correct/supersede/retire writes exist server-side (publishRevision, retireTerm, …) but are not wired into this UI: their request envelopes are deep enough (node/revision/domain-reference shape) that authoring them blind risked shipping a button that silently sends wrong data.

Chat — getContext / answerChat (#32)

Ask

This calls answerChat, which composes the SAME context above and then calls an injected model. This deployment (composeKnowledgeAccess) does not configure a model, so the server-side default (() => mapModelFailure()) answers writer_unavailable for every question — that is a real, honestly-surfaced 503 from the running code, not a mock. Expect it here until a model is wired at the composition layer.

Search — memories dataset (/api/search)

This is the OLDER memories bank, a different dataset from the knowledge kernel above. It is reused here because it is the only endpoint on this server with a real, working keyword-vs-semantic mode toggle.

Conclusions

Not implemented. No conclusion/observation table or kernel method is exposed by this transport (`registry.ts`) or by `publication/service.ts`'s bundles. Rendering a Conclusions view here would have nothing real to fetch.

Traces

Not implemented. `trace.ts` exists in `src/publication/` but the trace kernel is explicitly excluded from `KNOWLEDGE_METHODS` ("mid-integration elsewhere", registry.ts) — there is no route to call.

History

Not implemented. `getAcceptedHead` / `listAcceptedHistory` exist and ARE wired into the registry, but both require a `node_id` this UI has no way to discover (no listing endpoint, and node ids are not exposed anywhere else in this transport). Wiring a lookup-by-id-only history view without ever being able to obtain a valid id would render an always-empty form, which is worse than an honest "not implemented."
