# Offline retrieval metrics

Standard-library evaluator for issue #52, under parent #7. It scores a
retrieval-run document that something else produced.

It does not run retrieval. No model, no index, no query, no network, no live
dataset, no dependency outside the Python standard library. Given identical
bytes it returns an identical result — that is the point, because a number
nobody can reproduce is not evidence.

**This does not close #7 and makes no claim about retrieval quality.** Executing
real retrieval, approving a held-out corpus, the Thai substring product
regression, and the ICU-versus-trigram comparison and its acceptance all remain
separate work.

## Use

```
cd app/benchmarks
python retrieval_metrics.py INPUT.json          # one JSON result on stdout
```

Invalid input exits non-zero and prints exactly `invalid benchmark input` on
stderr — no partial metrics, and no fragment of the rejected document. The
input file is read only; nothing is ever written except stdout.

As a module:

```python
from retrieval_metrics import BenchmarkInputError, evaluate
result = evaluate(document_bytes)      # bytes in, dict out
```

Importing the module performs no I/O.

## Input

Strict UTF-8 JSON, at most 16 MiB of raw bytes (exactly 16 MiB is accepted).
Duplicate object keys, unpaired surrogates and non-finite numbers are refused.
Every named object is closed — an unexpected key is an error, not something to
ignore.

```jsonc
{
  "version": "arra-retrieval-eval/v1",
  "provenance": { "label": "...", "held_out": true },
  "corpus":  [ { "id": "c1" } ],
  "queries": [ { "id": "q1", "lang": "en", "purpose": "semantic", "relevant_ids": ["c1"] } ],
  "runs": {
    "icu":     [ { "query_id": "q1", "status": "complete", "ranking": ["c1"] } ],
    "trigram": [ { "query_id": "q1", "status": "complete", "ranking": ["c1"] } ],
    "vector":  [ { "query_id": "q1", "status": "complete", "ranking": [] } ]
  }
}
```

`lang` is `en` or `th`; `purpose` is `semantic` or `literal`. Each profile needs
exactly one entry per query — a missing, extra or duplicated entry fails the
whole evaluation, as does any status other than `complete`.

## What the numbers mean, and what they refuse to mean

* **Reciprocal rank** is `1 / rank of the first relevant document`, over the
  full ranking, 1-based, `0` when none is found. It is **not** truncated at the
  cutoff: a hit at rank 21 is worse than rank 1 and better than nothing, and
  truncating would report those last two identically.
* **recall@20** counts a query's relevant documents in the first 20, divided by
  how many it has.
* **Fusion** (`rrf_icu_vector`, `rrf_trigram_vector`) sums `1/(60 + rank)` over
  the two rankings for every id that actually appears. An absent id contributes
  nothing and is never given an invented rank.
* **An empty COMPLETE ranking is a real zero.** A profile that answered with
  nothing is a measurement. A profile that did not answer is refused instead.
* **An empty group is `null`, never `0`.** A language with no semantic queries
  has no mean, and `0.0` would read as "measured, scored nothing".
* **Literal probes are excluded from every aggregate**, while still being
  reported per query. They check exact-substring behaviour, not semantic
  quality, so averaging them in would mix two different questions.
* **`provenance.held_out` is a caller's declaration.** Nothing here verifies it,
  so every result carries `provenance_verification: "not_verified"` regardless
  of what was claimed. Accepting the claim is not checking it.

Two arithmetic decisions that are traps rather than defaults: fusion scores are
exact `Fraction`s, because two ids genuinely tie at `1/61` and float
accumulation would sometimes separate them by one ulp; and ties break on
**UTF-16 code units** (JavaScript string order), not Python codepoint order,
which disagree for supplementary characters.

## Multi-method harness (`harness_metrics.py`, `harness_corpus.py`, `harness_runner.py`, `harness_manifest.py`)

The evaluator above scores one frozen three-profile dispatch document. The
harness modules are the repeatable, pluggable layer #7 also asks for: any
number of retrieval methods, a mandatory null baseline, language-grouped
summaries, and structurally enforced provenance origins. They are separate
files, not an edit to `retrieval_metrics.py`, because that dispatch is
frozen for #52.

* **`harness_metrics.py`** — MRR, recall@k, precision@k and RRF fusion, all
  method-agnostic (no fixed profile names) and all at whatever cutoffs the
  caller asks for. Standard library only. `RRF_K = 60`, ties break on UTF-16
  code units.
* **`harness_corpus.py`** — loads a corpus and a qrels file with a
  provenance `origin` stamped by which loader function you call, never by a
  field in the payload:
  * Corpus: `load_synthetic_corpus` / `load_agent_authored_corpus` /
    `load_user_derived_corpus` stamp `corpus_origin` = `synthetic` /
    `agent_authored` / `user_derived` respectively. Documents carry
    `id`/`title`/`type`/`body`/`lang`, not just an opaque id, so the exact
    text a benchmark indexes is part of the frozen, hashable artifact.
  * Qrels: `load_agent_authored_qrels(payload, held_out=...)` /
    `load_independently_judged_qrels(payload, held_out=...)` stamp
    `qrels_origin` = `agent_authored` / `independently_judged`. `held_out`
    is a REQUIRED keyword on both — there is no default, so a caller must
    say explicitly whether the queries were authored without seeing the
    corpus.
  * `bind_qrels(corpus, qrels, for_report_qrels_origin=...)` refuses a
    relevant id absent from the corpus, AND refuses to bind qrels for a
    report that would claim a `qrels_origin` other than the one the qrels
    loader actually stamped — concretely, **agent-authored qrels can never
    be bound for a report labelled `independently_judged`**, no matter what
    an operator script hard-codes.
* **`harness_manifest.py`** — `validate_manifest(manifest)` enforces the
  REQUIRED manifest keys (`engine`, `tokenizers`, `indexed_text_composition`,
  `candidate_limit`, `eligibility_filter`, `embedding`, `artifact_sha256`,
  `rrf`, each with their own required sub-keys). A present key whose value
  is `None` is fine (e.g. `embedding.model` when the vector profile did not
  run) — only a MISSING key is refused.
* **`harness_runner.py`** — `run_benchmark(corpus, qrels, methods, manifest, fuse=...)`:
  * `manifest` is REQUIRED and validated FIRST — a missing required key
    refuses the whole call before any metric is computed, and a full
    manifest is echoed into the report unchanged (`report["manifest"]`).
  * Summaries are grouped by language: `summary.en` / `summary.th` /
    `summary.all`, computed over SEMANTIC queries only (`purpose !=
    "literal"`). A literal probe (e.g. the Thai inside-word discriminator)
    is still reported per query, just never folded into a macro mean.
  * A method's per-query outcome is `complete` (a ranking, possibly `[]` —
    a real, scored zero), `error` (preserved and counted, never scored as
    zero), or the WHOLE method can be `not_run` (e.g.
    `{"status": "not_run", "reason": "no frozen vectors"}` when there is no
    vector profile to measure). `not_run` summary values are `None`,
    **never `0`**.
  * RRF fusion (`fuse=[(fused_name, method_a, method_b), ...]`) scores the
    fusion as just another method; if either component did not run or
    errored for a query, the fused entry for that query carries the same
    status rather than silently fusing partial data.
  * **Always** computes and reports a deterministic null baseline
    (`null_random`) and a `delta_from_null` per language group per method
    per cutoff. MRR and recall are not interpretable without that null.

A small hand-authored fixture lives at
`fixtures/harness-v1/synthetic-example.json` (corpus `synthetic`, qrels
`agent_authored`, not held out), loaded end to end by
`test_harness_runner.py`. It exercises the plumbing only — it proves the
harness reports each method separately (so a candidate RRF fusion can be
seen scoring below the method that's actually doing the work, matching what
the fleet measured on a real session corpus: FTS wins known-item, embeddings
win paraphrase, and fusion loses both ways). **It is not evidence about
which retrieval method is good** — that requires a real held-out,
independently-judged corpus; see "Phase B" below.

Run the harness tests the same way as the evaluator's (`PYTHONDONTWRITEBYTECODE=1`
keeps `__pycache__` out of this gitignored-but-still-annoying directory):


## LanceDB executor (`run_lance.ts`)

`run_lance.ts` is a Bun script that drives REAL LanceDB retrieval -- not a
simulation -- over a corpus + query set, and writes `runs.json` +
`manifest.json` for the Python harness above to score. It runs no scoring
itself.

It uses `@lancedb/lancedb` 0.38.0 straight out of `app/server/node_modules`
(by relative import path -- `app/benchmarks` has no `package.json` of its
own; TS owns search in this codebase, so the product's own pinned SDK
measures the product's own profile, not the Python venv's different
`lancedb` 0.39.0 install). Every run opens a fresh `mktemp` LanceDB and
deletes it when done.

Four profiles, one shared candidate pool (`corpus size`) and one shared
eligibility filter (`workspace_name = 'bench'`), so the numbers are
comparable:

| Profile | What it is |
|---|---|
| `icu` | Exactly the product's CURRENT FTS config (`Index.fts({baseTokenizer:"icu"})`, mirroring `app/server/src/db.ts:112`). Duplicated locally with a `TODO(#30)` to import once `db.ts` exports it as a shared constant. |
| `ngram3` | `ngram(3,3)`, no stemming, no stop-word removal, per ruling R14. Duplicated locally with a `TODO(fts-ngram slice)` -- no shared `FTS_INDEX_OPTIONS` module exists on this base (`rg FTS_INDEX_OPTIONS app/server/src` finds nothing). |
| `literal_includes` | Exact case-folded substring scan. Labelled `literal`, **never** `trigram` -- LanceDB's `ngram` profile is still tokenized BM25 (measured in `LANCEDB-FACTS.md`), not a literal substring engine. |
| `vector` | `tbl.vectorSearch(...)` over PRECOMPUTED, FROZEN vectors read from a file. **No model call, ever** -- with no vectors file the profile reports `not_run` with a reason, and the manifest's `embedding.status` is `"not_run"`. Tests always stub the vectors file (`fixtures/run-lance-v1/vectors.json`); nothing in this repo's tests calls Ollama. |

The indexed text is `${title}\n\n${body}` (`INDEXED_TEXT_COMPOSITION`),
mirroring `app/server/src/publication/service.indexRevisionChunks.ts:62`
exactly -- title-only terms must be found, guarding against the legacy
`memories` table's `content`-only drift (`db.ts:111`).

Every FTS profile's manifest entry is the ACTUAL index configuration read
back from `table.listIndices()[].indexDetails`, not the options object this
script requested -- LanceDB fills in defaults the request left unset
(measured: `stem`/`removeStopWords`/`asciiFolding` default `true` even for
profiles that didn't ask for them). Every corpus/queries/qrels/vectors file
this run consumed is sha256-hashed into `manifest.artifact_sha256`.

Input file shapes:

```jsonc
// corpus.json -- SAME shape harness_corpus.py's loaders accept
{
  "provenance": {"label": "...", "source": "...", "created": "..."},
  "documents": [{"id": "c1", "title": "...", "type": "note", "body": "...", "lang": "en"}]
}
// queries.json -- query TEXT, distinct from qrels.json's relevance judgments
{
  "provenance": {"label": "...", "source": "...", "created": "..."},
  "queries": [{"id": "q1", "text": "...", "lang": "en", "purpose": "semantic"}]
}
// vectors.json -- precomputed, frozen; produced by an operator, never at test time
{
  "model": "all-minilm", "dims": 384, "distance": "l2", "normalization": "none",
  "ollama_digest": "sha256:...",
  "corpus": {"c1": [0.1, 0.2, "... 384 floats"]},
  "queries": {"q1": [0.1, 0.2, "... 384 floats"]}
}
```

Run it:

```
bun run app/benchmarks/run_lance.ts \
  --corpus  path/to/corpus.json \
  --queries path/to/queries.json \
  --qrels   path/to/qrels.json \
  --vectors path/to/vectors.json \
  --out-runs runs.json --out-manifest manifest.json
```

`--vectors` is optional; omit it (or the file) and `vector` reports
`not_run` instead of failing the run. Typecheck this directory on its own
(it is outside `app/server`'s `tsconfig.json`):

```
cd app/benchmarks && tsc --project tsconfig.json
```

Tests (`test_run_lance.test.ts`) use ONLY the tiny synthetic fixtures in
`fixtures/run-lance-v1/` -- hand-authored, labelled `SYNTHETIC`, not held
out, not evidence about retrieval quality:

```
cd app/benchmarks && bun test test_run_lance.test.ts
```

## Phase B — what Nat must supply, and how to run a real report

Phase A (everything above) is agent-buildable and asks nothing of anyone.
**Phase A tests alone are not evidence about retrieval quality and must
never be read as a number for #7** — they exist to prove the harness's
bookkeeping, exactly like the frozen evaluator's tests above.

Closing #7 needs, from Nat, local and NEVER committed (only digests are):

1. **A corpus** (~200 rows, per SPEC.md's target): real Thai/English
   memory-shaped content Nat owns or has consent for. Written as
   `corpus.json` in the shape above, loaded with
   `harness_corpus.load_user_derived_corpus` (or
   `load_agent_authored_corpus` if an agent drafted it under supervision —
   name it honestly).
2. **Held-out queries**: written without the corpus visible to whoever
   wrote them, as the `text` field in `queries.json` above.
3. **Independent relevance judgments**: written by someone other than
   whoever authored the corpus or the queries, as `qrels.json` (the
   `harness_corpus.Qrels` shape: `queries: [{id, relevant_ids, lang,
   purpose}]`), loaded with `harness_corpus.load_independently_judged_qrels(...,
   held_out=True)`. **`bind_qrels` will refuse this qrels file if it was
   instead loaded as `load_agent_authored_qrels`** — the origin travels
   with the loader call, never a typo-able field.
4. **A frozen vectors file** (`vectors.json` above): run an
   operator-invoked embedding step once (through Ollama, using the same
   `all-minilm@384` the product uses — `bge-m3@1024` is SPEC's candidate
   but does not fit the product's pinned 384-dim column and would need its
   own benchmark-only table). This repo does not ship that embedding step
   yet (`freeze_vectors.ts` — see "Not built" below); until it exists, embed
   the corpus and queries once through `embed.ts`'s exact request shape and
   write Float32 vectors + the Ollama model digest (`GET /api/show`) by
   hand into `vectors.json`.

Then, to produce a report:

```
cd app/benchmarks
bun run run_lance.ts --corpus corpus.json --queries queries.json \
  --qrels qrels.json --vectors vectors.json \
  --out-runs runs.json --out-manifest manifest.json
```

```python
# score_report.py -- not a committed script; this is the whole thing.
import json
from harness_corpus import bind_qrels, load_user_derived_corpus, load_independently_judged_qrels
from harness_runner import run_benchmark

corpus = load_user_derived_corpus(json.load(open("corpus.json")))
qrels = bind_qrels(
    corpus,
    load_independently_judged_qrels(json.load(open("qrels.json")), held_out=True),
    for_report_qrels_origin="independently_judged",
)
runs = json.load(open("runs.json"))["methods"]
manifest = json.load(open("manifest.json"))
report = run_benchmark(corpus, qrels, runs, manifest, fuse=[
    ("rrf_icu_vector", "icu", "vector"),
    ("rrf_ngram3_vector", "ngram3", "vector"),
])
print(json.dumps(report, indent=2))
```

**Never commit `corpus.json`, `queries.json`, `qrels.json` or `vectors.json`
from a real Phase B run.** Only `manifest.json` (which contains sha256
digests, never content) and the final `report` are safe to commit or post.
