# Offline retrieval metrics

Standard-library evaluator for issue #52, under parent #7. It scores a
retrieval-run document that something else produced.

It does not run retrieval. No model, no index, no query, no network, no live
dataset, no dependency outside the Python standard library. Given identical
bytes it returns an identical result — that is the point, because a number
nobody can reproduce is not evidence.

**This does not close #7 and makes no claim about retrieval quality.** Executing
real retrieval, approving a held-out corpus, the Thai substring product
regression, and the ICU-versus-trigram comparison and its acceptance all remain
separate work.

## Use

```
cd app/benchmarks
python retrieval_metrics.py INPUT.json          # one JSON result on stdout
```

Invalid input exits non-zero and prints exactly `invalid benchmark input` on
stderr — no partial metrics, and no fragment of the rejected document. The
input file is read only; nothing is ever written except stdout.

As a module:

```python
from retrieval_metrics import BenchmarkInputError, evaluate
result = evaluate(document_bytes)      # bytes in, dict out
```

Importing the module performs no I/O.

## Input

Strict UTF-8 JSON, at most 16 MiB of raw bytes (exactly 16 MiB is accepted).
Duplicate object keys, unpaired surrogates and non-finite numbers are refused.
Every named object is closed — an unexpected key is an error, not something to
ignore.

```jsonc
{
  "version": "arra-retrieval-eval/v1",
  "provenance": { "label": "...", "held_out": true },
  "corpus":  [ { "id": "c1" } ],
  "queries": [ { "id": "q1", "lang": "en", "purpose": "semantic", "relevant_ids": ["c1"] } ],
  "runs": {
    "icu":     [ { "query_id": "q1", "status": "complete", "ranking": ["c1"] } ],
    "trigram": [ { "query_id": "q1", "status": "complete", "ranking": ["c1"] } ],
    "vector":  [ { "query_id": "q1", "status": "complete", "ranking": [] } ]
  }
}
```

`lang` is `en` or `th`; `purpose` is `semantic` or `literal`. Each profile needs
exactly one entry per query — a missing, extra or duplicated entry fails the
whole evaluation, as does any status other than `complete`.

## What the numbers mean, and what they refuse to mean

* **Reciprocal rank** is `1 / rank of the first relevant document`, over the
  full ranking, 1-based, `0` when none is found. It is **not** truncated at the
  cutoff: a hit at rank 21 is worse than rank 1 and better than nothing, and
  truncating would report those last two identically.
* **recall@20** counts a query's relevant documents in the first 20, divided by
  how many it has.
* **Fusion** (`rrf_icu_vector`, `rrf_trigram_vector`) sums `1/(60 + rank)` over
  the two rankings for every id that actually appears. An absent id contributes
  nothing and is never given an invented rank.
* **An empty COMPLETE ranking is a real zero.** A profile that answered with
  nothing is a measurement. A profile that did not answer is refused instead.
* **An empty group is `null`, never `0`.** A language with no semantic queries
  has no mean, and `0.0` would read as "measured, scored nothing".
* **Literal probes are excluded from every aggregate**, while still being
  reported per query. They check exact-substring behaviour, not semantic
  quality, so averaging them in would mix two different questions.
* **`provenance.held_out` is a caller's declaration.** Nothing here verifies it,
  so every result carries `provenance_verification: "not_verified"` regardless
  of what was claimed. Accepting the claim is not checking it.

Two arithmetic decisions that are traps rather than defaults: fusion scores are
exact `Fraction`s, because two ids genuinely tie at `1/61` and float
accumulation would sometimes separate them by one ulp; and ties break on
**UTF-16 code units** (JavaScript string order), not Python codepoint order,
which disagree for supplementary characters.

## Tests

The suite lives outside any discovery root this repo uses, so invoke it
explicitly:

```
cd app/benchmarks
python -W error::ResourceWarning test_retrieval_metrics.py -v
```

Golden answers in `fixtures/retrieval-metrics-v1/known-answers.json` were
hand-calculated and are stored as exact `[numerator, denominator]` rationals;
the test converts them to float itself, so the expectation never borrows the
implementation's arithmetic. Nothing in that file was generated by the module
under test.
