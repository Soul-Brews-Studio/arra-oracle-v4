# Honcho table diff: v4 target-19 tier-1 vs stock Honcho v3.2.0

Issue #8, ruling R15 (2026-09-27 table-level update). Measured 2026-09-27 on m5.

## Conclusion

**"Byte-compatible" is FALSE as stated.** A plain dump of v4's tier-1 tables
does not load into stock Honcho unchanged: the first INSERT that uses v4's own
column names fails.

**What holds is narrow: TRUE WITH CONVERSIONS, for ONE bank imported into an
EMPTY stock Honcho, only when its workspace id is already nanoid21, and with
10 v4 columns lost.** Under exactly those conditions, and after the conversions
below, all 10 messages, 3 peers, 2 sessions, 5 memberships and the workspace
load into a fresh stock Honcho database. They then read back through Honcho's
REST API and through SQL with no missing rows and no changed values. Outside
those conditions the import fails: a second bank, or any Honcho that already
holds messages, collides on `pk_messages` (fact 5), and a workspace id that is
not nanoid21 is rejected by a CHECK (fact 6). 10 v4 columns have no Honcho
column and are lost (fact 7).

Measured facts behind that verdict:

| # | Fact | Consequence |
|---|---|---|
| 1 | v4 stores `h_metadata`. Honcho's SQL column is `metadata`; `h_metadata` is only the SQLAlchemy attribute name in `src/models.py`. The live INSERT fails with `column "h_metadata" of relation "workspaces" does not exist`. | Rename needed on 4 tables. This alone makes the literal claim false. |
| 2 | v4 JSON columns are nullable UTF-8 text. Honcho's are `jsonb NOT NULL DEFAULT '{}'`. | Parse to jsonb. NULL becomes `{}`, so the difference between NULL and `{}` is lost. jsonb keeps the JSON value but not the text: `'{"b": 1,  "a":2}'::jsonb::text` returns `{"a": 2, "b": 1}`. |
| 3 | v4 timestamps are `timestamp[us]` with no time zone (UTC by v4 convention). Honcho uses `timestamptz`. | Attach `+00:00`. Both keep microseconds, so the instant survives exactly. |
| 4 | `messages.token_count`: v4 int64, Honcho `integer` (int32). | Narrowing. Values outside int32 are refused. |
| 5 | `messages.id`: v4 int64 is per-dataset legacy order (1..n). Honcho's is one `GENERATED BY DEFAULT AS IDENTITY` for the whole database. | Ids load unchanged into an empty database, but the sequence must be moved past them with `setval`. A second bank, or any Honcho that already holds messages, collides on `pk_messages`. This was measured live: once by accident (REST leg first, then the table leg), and again on purpose by the test's second bank. Renumbering would lose the v4 value. |
| 6 | Honcho enforces `CHECK length(id) = 21 AND id ~ '^[A-Za-z0-9_-]+$'` on workspaces, peers, sessions and `messages.public_id`. | v4 requires nanoid21 for peer and session ids and for `public_id`, so those load unchanged. **v4 does not constrain `workspaces.id`.** Its own dev seed `ws_default_devseed` (18 chars) would be rejected, so an id map is needed. |
| 7 | 10 v4 columns have no column in stock Honcho: `workspaces.mission`, `messages.role/in_reply_to/read/read_at`, `source_namespace/source_message_id/source_payload_digest/source_created_at`, and `ingested_at` (NOT NULL). | Dropped from the dump, so they are lost. |
| 8 | Honcho's REST name pattern `^[a-zA-Z0-9_-]+$` is **not** a table constraint. | The federation peer `m5:arra-oracle-v3` loads raw. REST reads it back byte-exact, with no hnb64 encoding, even though a REST *write* of that name is refused. |
| 9 | Postgres `text` cannot store U+0000. Honcho has `CHECK length(content) <= 65535`. | Such values are refused, never stripped (`table_sql.IncompatibleValueError`). |
| 10 | `GET .../sessions/{id}/peers` does not list a membership row whose `left_at` is set. | Honcho gives `left_at` the same meaning v4 does. The departed peer stays in the table, but REST does not show it. |
| 11 | Honcho keeps working on the imported rows. After `setval`, a REST message write gets the next identity id with no collision. REST lists messages in `seq_in_session` order. | Only for an import into an empty database (see 5). |

## How it was measured

- **Honcho side**: `information_schema.columns` and `pg_constraint` of the live
  database. This is a disposable Honcho built from tag `v3.2.0`, with HEAD
  checked to equal `210b56cf953fcf447ffafcb428d4b4f1823b83fd`. Only the api and
  database services run (plus the redis they depend on), bound to 127.0.0.1,
  after the api container's alembic upgrade. Postgres is 15.19. The snapshot is
  `table_map.HONCHO_V3_2_0_COLUMNS`, and the live test re-reads the schema and
  fails if it drifts.
- **v4 side**: the Arrow schema of `arra_migrate.target_v1.core`, i.e. the
  target-19 `TARGET_SCHEMA` for these five tables.
- **Round trip**: `tests/test_honcho_table.py::TestLiveTableRoundTrip`. It is
  gated on `HONCHO_ROUNDTRIP_LIVE_BASE_URL`, like `TestLiveRoundTrip`, plus the
  compose project the harness stood up. The steps:
  1. It writes the SPEC §15.5 bank as a real target-19 Lance dataset in
     `mktemp -d`, using `tests/honcho_table_bank.py` with nanoid21 ids and the
     `source_*`/`ingested_at` columns filled.
  2. It reads the bank back with `dump.dump_tier1`.
  3. It converts the rows with `table_sql.bundle_to_honcho_sql`, applying only
     the conversions in the table below.
  4. It pipes the SQL into `docker compose exec -T database psql -v ON_ERROR_STOP=1`.
  5. It reads everything back through `HttpHonchoTarget` (REST) and through SQL
     (`json_agg`), and diffs against the input in `table_measure.measure_table_round_trip`.
  6. It asserts that the measured per-field outcome equals `table_map.EXPECTED_OUTCOMES`.
- **Harness**: `bash app/just/honcho-live.sh` runs the table leg first, on the
  fresh database, then the REST leg (`TestLiveRoundTrip`). It always tears down
  containers, volumes, the `/tmp/honcho-roundtrip-pin` clone and the built image.
  It refuses to start if anything already answers on 127.0.0.1:8000, or if
  127.0.0.1:5432 or :6379 (which the compose also publishes) is in use. It never
  touches white.local.

## Column-by-column diff

Verdict key: **exact** means same name, compatible type and nullability, and
every value v4 can hold loads unchanged. **convertible** means a documented,
deterministic conversion is required. **incompatible** means there is no stock
column for it, or no conversion keeps the value.

Outcome key, measured live: *rest* is the read-back through Honcho's REST API,
*table* is the read-back through SQL.

- *exact*: same value; for text, the same code points and so the same UTF-8 bytes.
- *converted*: equal only after the conversion.
- *not-exposed*: the REST schema has no field for the column.
- *lost*: no Honcho column holds the value.

## What byte for byte means here, by field

- **Survive byte for byte** (same value through SQL; through REST as well
  where REST exposes the field):
  - every name and key column;
  - `content`;
  - `public_id`;
  - peer and session `id` (SQL only);
  - workspace `id`, only because the bank's is nanoid21 (SQL only);
  - `messages.id` (SQL only, empty database only);
  - `seq_in_session` (SQL only);
  - `token_count`;
  - `is_active`.
- **Survive after conversion**:
  - 6 timestamp columns (the four `created_at`, plus `joined_at` and
    `left_at`): the instant is exact to the microsecond, but the type changes
    from naive to tz-aware. The other three v4 timestamps (`read_at`,
    `source_created_at`, `ingested_at`) have no Honcho column and are lost;
  - 13 JSON columns: the JSON value survives, but the text bytes, key order and
    NULL do not.
- **Lost**: 10 v4 columns have no Honcho column (Honcho column `none` in the
  tables above).
- **Not exposed by REST, though kept in the table**:
  - every `internal_metadata`;
  - the v4 `id`s;
  - `seq_in_session`;
  - `session_peers.configuration`, `joined_at` and `left_at`.

## Compared with the REST leg (`TestLiveRoundTrip`)

The table leg keeps several things the REST interchange cannot carry:

- historical `created_at` on three entity tables (workspaces, peers, sessions), and µs rather than ms precision on `messages.created_at`, which REST carries only to ms *(driver correction 2026-09-27: `messages.created_at` has no `LOSSY_FIELDS` entry, and TestLiveRoundTrip compares it strictly)*;
- `messages.public_id` and `token_count`;
- `session_peers.joined_at`, `left_at` and `configuration`;
- every `internal_metadata`;
- raw federation names, with no hnb64 encoding.

The REST leg keeps one thing the table leg loses. It carries `role`,
`in_reply_to`, `read` and `read_at` through the `metadata._v4` fold
(`bundle._message_payload`, `FOLD_KEY`), the extension point SPEC §15.2
invariant 5 prescribes. The table leg drops those four columns. It could apply
the same fold, since that is a conversion into `metadata`, but then Honcho's
`metadata` would no longer equal v4's `h_metadata`, so this measurement does not.

The table leg also pays four costs:

- it needs direct access to Honcho's database;
- it needs the `h_metadata` rename;
- it needs nanoid21 workspace ids;
- it needs an empty messages identity range.

## Fix round 2026-09-27

An independent verifier refuted the first version of this slice. What changed:

- **The comparator is now shown to fail.** The live test's "0 problems, outcomes
  equal `EXPECTED_OUTCOMES`" used to rest on a comparator no test could fail.
  `tests/test_honcho_table_measure.py` now feeds `measure_table_round_trip` a
  faithful offline stand-in for stock Honcho after the import. It measures as
  documented, and then one corruption per comparison, on each read path, must
  be reported:
  - text `+X`;
  - `token_count` as a string;
  - a timestamp 1 µs later;
  - a NULL `left_at` that came back set;
  - a changed JSON value;
  - a NULL JSON that did not become `{}`;
  - a missing or extra row;
  - a hidden active member;
  - reversed message order.

  Each of six comparison removals (timestamp, JSON, exact, order, SQL row set,
  REST row set), applied one at a time, fails at least one of these tests.
- **Counts corrected.** It is 10 lost columns, not 11, and 6 timestamp columns
  survive by conversion, not 13. `DiffDocMatchesTheMapTests` now checks this
  file's per-column rows and headline counts against `table_map`.
- **`workspaces.id` is now incompatible, not convertible.** The generator applies
  no conversion to it; it refuses any value that is not nanoid21.
- **Headline narrowed** to the conditions it was measured under.
- **Generator**: JSON text holding a number Python reads as non-finite (`1e400`,
  `NaN`, `Infinity`) is now refused. jsonb keeps `1e400` as an exact numeric
  that reads back as a different value, and rejects the other two.
- **Style debt, disclosed** (PROOF.md §5): `table_measure.py` exports
  `read_rows_sql`, `measure_table_round_trip` and `TableReport`. `table_sql.py`
  exports `bundle_to_honcho_sql` and `IncompatibleValueError`. `table_map.py`
  exports the map constants. None of the three is named after one function.
  This follows the existing `honcho_roundtrip` package idiom (`bundle.py`,
  `diff.py`, `target.py`), and every file is under 500 lines.
